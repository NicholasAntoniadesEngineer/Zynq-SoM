## P0 FINDING — the SoM is a 4.2–5 V module; the carrier feeds J1 VIN 20 V

**This must be fixed before any board is powered. It outranks everything
else in this document (LAW 0).**

- The SoM input net `VIN` (J1 pins 1–14) feeds, with **no pre-regulator**:
  - U13 **TPS7A20** (IN *and* EN on VIN) -> `+3V3_SC`
    [som: VIN: U13.4 (IN), U13.3 (EN); +3V3_SC: U13.1 (OUT)] — abs-max 6 V.
  - U6 **MPM3834** -> `+3V3` and U4 **MPM3834** -> `+1V8`
    [som: VIN: U4.12/13/14, U6.12/13/14; +3V3: U6.9/10 (OUT); +1V8:
    U4.9/10 (OUT)] — MPM38xx is MPS's 6 V-input module family.
  - U10 **MPM3822** -> `+1V35` (DDR3L) [som: VIN: U10.13/14; +1V35:
    U10.3/10] — 6 V family.
  - U8 **TPSM82864** -> `+1V0` (core) [som: VIN: U8.21/22; +1V0:
    U8.12–15] — TI 2.7–6 V module.
- The SoM's own power-architecture sheet annotates the input
  **"4.2-5V"** (`som/schematic/power_architecture.kicad_sch`, text at
  223.9,44.45).
- The carrier binds J1.1–14 to **+VIN** — the USB-C PD rail the PLAN locks
  at **20 V** (`carrier/som_conn_gen.py` RAIL_SPELLING {"VIN": "+VIN"};
  `carrier/reports/link_report.txt` "+VIN … -> SoM 14 pins";
  `carrier/docs/BRINGUP.md` stage 1 "+VIN rises to the negotiated 20 V").

At the first successful PD contract, 20 V lands on five 6 V-max regulators:
the SoM is destroyed. ERC, overlap, power-tree and SPICE gates all pass
today because the binding is *consistent* — it is consistently wrong.

**Resolution (recommended, needs user sign-off — adds one regulator):**
1. New **always-on +5V_SOM stage** in `power.py`: third TPS54302DDCR
   (same proven cell as U1/U2) fed from +VIN, EN strapped on (UVLO divider,
   NO bring-up cell), output set 5.0 V, budget 3 A.
2. `som_conn_gen.py` RAIL_SPELLING becomes `{"VIN": "+5V_SOM"}`;
   `c.draws("+5V_SOM", 2.0, "SoM ~10 W class at 5 V")`.
3. Why always-on and not DIP-gated: the PD negotiation chain is
   FUSB302 (carrier, +3V3_SC) mastered by the SoM SC (U9), and +3V3_SC is
   generated ON the SoM from its VIN [som above]. If SoM VIN waits for a
   DIP, the SC is dead, nobody negotiates PD, and 20 V never arrives —
   circular. At default 5 V VBUS the buck runs at ~100 % duty and passes
   ~4.7–4.8 V (inside the SoM's 4.2–5 V window); after the 20 V contract it
   regulates 5.0 V. The "switches-only stage 1 with a blank SC" contract
   (PLAN bring-up architecture) is preserved: +5V_SOM behaves exactly like
   +3V3_SC — alive pre-DIP by design.
4. Regenerate: power tree (the +VIN draw entry "SoM module … at 20 V" in
   som_conn_gen is wrong twice over), BRINGUP.md stage 0/1, FIRMWARE header
   rail table, J1 sheet, goldens.

Corollary fix: `schgen/powertree.py:119` models `+3V3_SC` as
"SoM MPM3822 … 2.0 A". Netlist truth: +3V3_SC is the **TPS7A20 LDO U13**
(300 mA class — the SoM power-architecture sheet says "3V3 (300mA)"); the
MPM3822 is the **+1V35 DDR3L** rail. Carrier draw on +3V3_SC today is
~23 mA (sum of `draws()` across bringup_*/power_mon/usb_pd/debug_boot) —
safe, but the limit constant and its comment must be corrected to
0.3 A/TPS7A20 so the gate guards the real envelope.

### 1.1 The interrupt decision (GPIO4)

`STM32_FUSB302_INT` (usb_pd U1.5, open-drain) and `STM32_BRINGUP_INT`
(TCA9535 INT#, open-drain) **merge onto STM32_GPIO4 (PA15)** as one
wire-OR'd active-low interrupt. Rationale:

- Zero free GPIOs remain (table above), and both sources are open-drain
  devices **on the same I2C bus** — IRQ -> read both devices' status
  registers is the textbook pattern.
- PD timing tolerates it: the FUSB302B handles GoodCRC/retries in hardware;
  policy-level events have ms-scale budgets.
- Routing FUSB302 INT through a TCA9535 input instead would serialize a PD
  interrupt behind TWO bit-banged I2C transactions — strictly worse.
- Pull-up consolidation: today the merged net would carry usb_pd R1 (4k7,
  +3V3_SC) **and** bringup_rails (10k, +3V3_SC) = 3.2k combined. Legal, but
  one pull per net is the house rule: **delete usb_pd R1 at wave-3, keep
  the bringup_rails 10k** (bringup_rails owns the bus + INT pulls already).
- PA15's reset state is JTDI-with-pull-up (STM32G4 datasheet) — benign for
  an active-low INT input before firmware boots.

## 2. STM32_I2C2 — the SC bus binding (J1.49 / J1.55, bit-banged)

### 2.1 Hardware I2C is IMPOSSIBLE on the exported pins — proof

The G431's real I2C2 peripheral (PA8 = SDA, PA9 = SCL, AF4) is **consumed
on-module**: it is the SC <-> Zynq PS link — PA8/PA9 carry SoM nets
`STM32_SDA`/`STM32_SCL` to Zynq **PS_MIO15/PS_MIO14** (= PS I2C0) with 10k
pulls to SoM +3V3 and a 22R series on SCL
[som: STM32_SDA: U9.30 (PA8), U2.E6 (PS_MIO15_500), R87.2;
STM32_SCL: U9.31 (PA9), R86.2, R96.1; R96.2 -> STM32_SCL_T].
They are NOT on J1/J2/J3.

Exhaustive AF check of the ten exported pins (STM32G431 datasheet AF table):

| Exported pin | I2C alternate function | Verdict |
|---|---|---|
| PC11 (GPIO1) | I2C3_SDA (AF8) | SCL mate (PA8/PC8) not exported / not bonded |
| PB5 (GPIO2) | I2C3_SDA (AF8) | same — no exported I2C3_SCL exists |
| PC10 (GPIO3) | none | — |
| PA15 (GPIO4) | I2C1_SCL (AF4) | only exported I2C1_SDA is **PA14 = SWCLK** (reserved, firmware contract) |
| PA14 (GPIO5) | I2C1_SDA (AF4) | RESERVED for SWD |
| PA13 (GPIO6) | I2C1_SCL? no — SWDIO | RESERVED for SWD |
| PB10 (GPIO7) | none (G4: no I2C on PB10) | BOOTSEL0 |
| PB11 (GPIO8) | none | BOOTSEL1 |
| PA4 (DAC1) | none | free |
| PA5 (DAC2) | none | free |

No SCL+SDA pair exists outside the SWD reservation. The bringup dossier's
risk R2 fallback is therefore THE design: **firmware bit-bang**.

### 2.2 Binding

- **STM32_I2C2_SDA = STM32_DAC1 = J1.49 = U9 PA4**
- **STM32_I2C2_SCL = STM32_DAC2 = J1.55 = U9 PA5**
  [som: STM32_DAC1: J1.49, U9.12 (PA4); STM32_DAC2: J1.55, U9.13 (PA5)]
- PA4/PA5 have no I2C AF — open-drain **GPIO bit-bang**, ~100 kHz target.
  Every slave tolerates it (FUSB302B: hardware GoodCRC/retries; TCA9535,
  INA3221, 24C02-class EEPROM: static slaves; 400 kHz is nowhere required).
- Cost: the DAC1/DAC2 analog outputs are sacrificed (no carrier subsystem
  ever claimed them — grep `STM32_DAC` in carrier/subsystems/ = zero hits).
- The net/bus name **STM32_I2C2 is kept** (23 sheets and the firmware
  header already use it); the generated header grows
  `ZC_I2C_BITBANG_SDA/SCL` constants documenting that this is a soft bus.

### 2.4 Pull-up single-point audit (the usb_pd/+3V3_SC R1 context)

grep-audited across carrier/subsystems/:

- **SDA/SCL pulls live EXACTLY ONCE**: bringup_rails 4k7 + 4k7 to
  **+3V3_SC** (`bringup_rails.py:113-114`). usb_pd contributes none
  (docstring records the dossier-R1 move — its R1 is the INT pull-up, now
  also on +3V3_SC); power_mon "adds NONE" (power_mon.md §2); fmc adds none
  (fmc.py §5 cites the bringup_rails single point). PASS.
- +3V3_SC is correct (PD must negotiate with every carrier rail down) and
  is alive pre-PD via the SoM TPS7A20 — but see the P0 finding: that is
  only true once SoM VIN is re-railed to +5V_SOM.
- After the GPIO4 wire-OR (section 1.1) the INT net would carry two pulls —
  delete usb_pd R1, keep bringup_rails' 10k (one pull per net).
- Bit-bang slew: 4k7 against a long-ish 5-sheet bus (FUSB302 + TCA9535 +
  2x INA3221 + FMC C30/C31) at 100 kHz is comfortable; if the FMC run adds
  too much C, the legal fix is lowering to 2x 2k2 at the same single point
  — never a second pull elsewhere.

### 3.1 +2V5_VADJ budget — the math, camera LP-RX included

Thermal envelope (fmc.md §3, TI TLV757P DS): DBV RthJA = 231 °C/W,
Tj ≤ 125 °C, Ta = 50 °C -> Pd ≤ 0.32 W; Pd = (3.3 − 2.5) V × I ->
**I ≤ 0.40 A continuous total**.

| Load on +2V5_VADJ | Current | Basis |
|---|---|---|
| FMC mezzanine VADJ allocation | 0.400 A | fmc.py `draws()` — **currently books the ENTIRE envelope** |
| Zynq bank-35 VCCO: 12 FMC LA pairs as LVDS_25 **outputs** | ~0.042 A | LVDS_25 drivers are current-mode, ~3.5 mA static each from VCCO (7-series SelectIO); inputs (CLK0/1_M2C, camera HS-RX) draw ~0 DC from VCCO — the 100R terminations are line-to-line |
| Camera HS-RX (3 LVDS_25 input pairs) | ~0 | input buffers; differential termination carries no VCCO DC |
| **Camera LP-RX (XAPP894 dividers, L16/L18 reserve)** | **~0** | the divider taps are resistive loads on the CAMERA's LP drivers down to GND — they draw from the cable signals, not from VCCO_35; the single-ended LVCMOS25 input buffers add no DC |
| Zynq bank-35 internal | mA-class | leakage/bank logic |
| PG_C2M 10k pull-up | 0.25 mA | fmc.py R2 |

So camera LP-RX is FREE on this rail — the verdict stands on the FMC side:
**0.400 (mezzanine) + ~0.045 (bank VCCO) > 0.400 envelope.** The honest fix
at wave-3: the J3 sheet declares `draws("+2V5_VADJ", 0.050, "Zynq bank-35
VCCO …")` when the rail-map bind lands, and fmc.py's mezzanine allocation
drops **0.400 -> 0.350 A** so the power-tree gate enforces the real DBV
envelope. (Escape hatch if a mezzanine needs more: TLV75725P**DRV**R,
RthJA 100 °C/W -> ~0.9 A — LCSC C507271, 16 units, ghost-risk; or a 2.5 V
buck stage.)

### 3.2 Round-5 rail isolation (context for the NC edit)

SoM-exported `+3V3` (J1.24–27) and `+1V8` (J1.56/58/60) are OUTPUTS of the
SoM's own MPM3834s [som: +3V3: U6.9/10 (OUT); +1V8: U4.9/10 (OUT)] — they
must NEVER be tied to the carrier's same-named buck/LDO rails (regulator
fight). Round-5 decision: explicit no-connect (or TP-only) on the carrier
J1 sheet; carrier sheets keep consuming the carrier rails by the same
names. Note for the implementer: after isolation the carrier microsd
TXS02612 VCCA (carrier +1V8) faces the SoM's 1.8 V SDIO bank (SoM +1V8,
VCCO_MIO1_501 [som: +1V8: U2.A10/B13/D9/E12]) — two different regulators,
same nominal, common GND: level-compatible, no action.

### 3.3 Two more SoM-side facts the J-sheet regen must honor

- **PUDC strap missing**: `IO_L3P_PUDC_34` (J3.39) is the bank-34
  pull-up-during-config pin and has **no resistor anywhere on the SoM**
  [som: IO_L3P_PUDC_34: J3.39, U2.K16 only]. UG470 requires it tied (high =
  IO pulls disabled during config, low = enabled). The function map keeps
  it OUT of the LCD bus (section 4) and the J3 regen must add a **10k
  strap to GND** (internal pull-ups during config — friendly to the LCD's
  "DISP defaults on" 10k and the active-low buttons) — carrier-side part,
  J3 sheet.
- VM0/VM1 (J1.40/J1.36): strapped on-SoM (section 1.3) — carrier NC,
  optional TPs (debug_boot dossier already says so; the J1 regen makes the
  NC explicit).

### 4.5 PS MIO function map (J1)

| J1 net | J1 pin | Zynq ball (live) | Wave-3 function |
|---|---|---|---|
| ZYNQ_PS_MIO10 | 42 | G7 (PS_MIO10_500) [som] | **ZYNQ_PS_UART0_RXD** (uart_bridge U1.21 — bridge TXD) |
| ZYNQ_PS_MIO11 | 48 | B4 (PS_MIO11_500) | **ZYNQ_PS_UART0_TXD** (uart_bridge U1.20) |
| ZYNQ_PS_MIO0 / 9 / 12 | 50 / 52 / 46 | G6 / C4 / C5 | spare PS GPIO (inventory, 1.3) |
| ZYNQ_PS_MIO7/VM0, MIO8\VM1 | 40, 36 | D5, E5 | NC / TP-only (strapped on-SoM) |

MIO10/11 is the ONLY complete UART0 MIO group among the exported pins
(UG585 MIO map: UART0 lands on pin pairs {10,11}, {14,15}, … — 14+ are not
on J1). RX/TX polarity within the pair (RXD = MIO10, TXD = MIO11) follows
the UG585 convention mirrored from UART1's TXD-on-even precedent (ZedBoard
UART1: TX = MIO48, RX = MIO49); **implementer must confirm against the
ps7 MIO L3_SEL table when generating the PS config — a swap is a 2-line
J1-sheet regen, both pins live on J1.** UART0 CTS/RTS have NO MIO route in
Zynq-7000 (modem signals are EMIO-only, UG585 §19) — hence the bank-13
EMIO pair in 4.1.

### 4.6 J-sheet regeneration spec (som_conn_gen.py) + gate implications

`som_conn_gen.py` gains one generated, committed table — `FUNCTION_MAP:
{som_contract_net: function_net}` — sourced from THIS document (and later
from nets.py). The connector circuits then emit the **function name** as
the port net for mapped pins (everything in 4.1–4.5), keep verbatim names
for unmapped/spare pins, and:

1. **Port renames** (the netlist actually changes on som_j1/j2/j3):
   - som_j1: STM32_GPIO1/2/3 -> STM32_RAIL_EN_5V0/3V3/1V8; STM32_GPIO4 ->
     SC_INT_N (consumed by BOTH bringup_rails:STM32_BRINGUP_INT and
     usb_pd:STM32_FUSB302_INT — the linker must accept a 2-consumer merge

   - GPIO5/6/7/8, NRST, BOOT0, ZYNQ_T*, SDIO_*, ETH_*, USB_* keep their
     contract names (already bound).
